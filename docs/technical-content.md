# Правила описания технического содержания

## 1. Назначение

Этот раздел устанавливает правила документирования технических аспектов проекта Design of an AI-Powered Information System: архитектуры, программных компонентов, API, конфигурации, баз данных, процессов развёртывания и моделей машинного обучения.

Документация должна отражать фактическое состояние реализации, а не предполагаемое или планируемое поведение системы.

## 2. Общие требования

Техническое описание должно отвечать на следующие вопросы, если они относятся к конкретному компоненту:

- Для чего предназначен компонент?
- Какие задачи он решает?
- Какие входные данные получает?
- Какие результаты формирует?
- С какими компонентами взаимодействует?
- Какие зависимости и ограничения имеет?
- Как его настроить, запустить или проверить?

Необходимо отделять реализованные функции от планируемых. Если описывается будущая функциональность, это должно быть явно указано.

## 3. Описание архитектуры

При описании архитектуры необходимо указывать назначение компонентов, их ответственность и способы взаимодействия.

Рекомендуется документировать:

- состав системы;
- назначение каждого основного компонента;
- связи между компонентами;
- используемые протоколы и форматы данных;
- внешние зависимости;
- основные архитектурные ограничения.

Диаграммы должны иметь понятные названия и пояснения. Если схема содержит условные обозначения, их необходимо объяснить.

Архитектурные решения и их обоснования рекомендуется фиксировать отдельно, чтобы было понятно, почему выбран конкретный подход.

## 4. Документирование API

Описание API должно содержать достаточно информации для использования интерфейса без изучения его исходного кода.

Для каждого endpoint рекомендуется указывать:

- HTTP-метод и путь;
- назначение операции;
- параметры пути и запроса;
- формат тела запроса, если оно предусмотрено;
- требования к авторизации;
- пример успешного ответа;
- возможные коды ошибок;
- ограничения и побочные эффекты, если они есть.

Пример оформления:

```http
GET /api/v1/items/{id}
```

Назначение: получение элемента по идентификатору.

Параметры:

| Параметр | Тип | Описание |
|---|---|---|
| `id` | string | Идентификатор элемента |

Пример ответа:

```json
{
  "id": "item-123",
  "name": "Example item"
}
```

Пример является иллюстративным. Перед публикацией его необходимо адаптировать к фактической схеме API проекта.

Не следует утверждать, что endpoint существует или поддерживает конкретный формат, если это не подтверждено реализацией.

## 5. Документирование кода

Примеры кода должны быть минимальными, понятными и связанными с описываемой задачей.

Необходимо:

- указывать язык программирования;
- использовать актуальные имена классов, методов и переменных;
- пояснять нетривиальную логику;
- показывать необходимые импорты или контекст, если без них пример непонятен;
- исключать неиспользуемый и заведомо ошибочный код;
- обозначать упрощения, если пример не является самостоятельным.

Комментарии должны объяснять назначение или причину нетривиального решения, а не просто повторять очевидное действие.

## 6. Конфигурация и переменные окружения

При описании конфигурации следует указывать имя параметра, его назначение, допустимый формат и наличие обязательного значения.

Пример:

| Параметр | Назначение | Обязательный |
|---|---|---|
| `PORT` | Порт приложения | Зависит от конфигурации |
| `DATABASE_URL` | Строка подключения к базе данных | Если используется подключение через URL |
| `LOG_LEVEL` | Уровень журналирования | Зависит от конфигурации |

Фактические параметры необходимо сверять с реализацией.

В документации нельзя публиковать реальные пароли, токены, приватные ключи и другие секретные значения. Для примеров следует использовать безопасные условные значения.

## 7. Базы данных и модели данных

При описании схемы базы данных необходимо указывать назначение сущностей, ключевые поля и связи между ними.

Если это важно для понимания системы, следует документировать:

- первичные и внешние ключи;
- ограничения целостности;
- обязательность полей;
- допустимые значения;
- правила удаления и обновления связанных записей;
- особенности миграций.

Примеры схем должны соответствовать актуальной версии модели данных.

## 8. Документация моделей машинного обучения

Описание модели машинного обучения должно позволять понять её назначение, исходные данные, способ оценки и ограничения.

Рекомендуется включать:

- задачу и назначение модели;
- источник и характеристики набора данных;
- этапы предварительной обработки;
- используемый алгоритм или архитектуру;
- процесс обучения;
- метрики оценки и результаты экспериментов;
- ограничения и известные риски;
- способ использования обученной модели;
- требования к воспроизводимости эксперимента.

При указании результатов необходимо сообщать условия эксперимента, состав данных и способ вычисления метрик. Не допускается представлять результаты одного эксперимента как универсальную гарантию качества модели.

## 9. Безопасность и обработка ошибок

Техническая документация должна описывать существенные ограничения безопасности, если они влияют на использование компонента.

При документировании ошибок необходимо указывать условия возникновения и ожидаемое поведение системы.

Не следует раскрывать чувствительные сведения, внутренние секреты или персональные данные в примерах, логах и скриншотах.

## 10. Проверка технической достоверности

Перед публикацией необходимо:

- [ ] Сверить описание с актуальной реализацией.
- [ ] Проверить команды и примеры кода.
- [ ] Проверить форматы запросов и ответов API.
- [ ] Проверить имена параметров конфигурации.
- [ ] Убедиться, что примеры не содержат секретов.
- [ ] Указать существенные ограничения.
- [ ] Проверить актуальность диаграмм и схем.
- [ ] Подтвердить условия и результаты экспериментов, если описывается ML-модель.
