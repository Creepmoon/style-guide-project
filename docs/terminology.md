# Правила использования терминологии

## 1. Назначение

Этот раздел определяет правила выбора, употребления и согласования терминов в документации проекта Design of an AI-Powered Information System.

Единая терминология помогает избежать неоднозначности и обеспечивает одинаковое понимание архитектуры, процессов и функций системы всеми участниками проекта.

## 2. Основные требования

При использовании терминов необходимо:

- выбирать точные и общепринятые обозначения;
- использовать один термин для одного понятия;
- не заменять термин синонимами без необходимости;
- объяснять специализированные понятия, если они могут быть неизвестны читателю;
- сохранять оригинальные имена программных сущностей;
- обновлять глоссарий при появлении новых понятий.

Если термин имеет несколько значений, следует определить его значение в контексте проекта.

## 3. Базовый глоссарий

| Термин                    | Определение и правила употребления                                                                                  |
|---------------------------|---------------------------------------------------------------------------------------------------------------------|
| Информационная система    | Совокупность программных и иных компонентов, обеспечивающих обработку и хранение информации для определённых задач. |
| Компонент                 | Отдельная часть системы с определённой ответственностью и интерфейсом взаимодействия.                               |
| Сервис                    | Компонент, предоставляющий определённые функции другим компонентам или пользователям.                               |
| API                       | Интерфейс, через который программные компоненты взаимодействуют друг с другом.                                      |
| REST API                  | API, спроектированный с использованием принципов REST.                                                              |
| HTTP                      | Протокол прикладного уровня для взаимодействия между клиентами и серверами.                                         |
| Клиент                    | Пользователь, приложение или компонент, отправляющий запросы к другому компоненту.                                  |
| Сервер                    | Компонент, принимающий запросы и предоставляющий соответствующие ответы или услуги.                                 |
| База данных               | Организованное хранилище данных, управляемое соответствующей системой.                                              |
| Модель данных             | Представление структуры данных и связей между ними.                                                                 |
| Модель машинного обучения | Объект, обученный на данных для выполнения задачи прогнозирования, классификации или другой целевой операции.       |
| Набор данных              | Совокупность данных, используемых для обучения, проверки или оценки модели.                                         |
| Обучение модели           | Процесс настройки параметров модели на основании данных и выбранного алгоритма.                                     |

| Метрика                   | Формализованный показатель, используемый для оценки свойства системы или качества модели.                           |
| Конфигурация              | Набор параметров, определяющих поведение компонента или системы.                                                    |
| Развёртывание             | Размещение и настройка программного компонента в целевой среде.                                                     |
| CI/CD                     | Практики и процессы автоматизированной проверки, сборки и доставки программных изменений.                           |
| Pull Request              | Запрос на рассмотрение и слияние изменений из одной ветки Git в другую.                                             |
| Ревью                     | Проверка изменений другим участником проекта перед их принятием.                                                    |

Приведённый глоссарий является базовым. Термины, относящиеся к конкретным подсистемам, добавляются по мере развития проекта.

## 4. Написание технических названий

Названия технологий и инструментов необходимо писать так, как они официально обозначаются.

Примеры:

- `Python`;
- `Java`;
- `Spring Boot`;
- `PostgreSQL`;
- `Docker`;
- `MkDocs`;
- `GitHub Actions`;
- `REST API`;
- `JSON`.

Не следует произвольно изменять регистр символов в названиях продуктов, языков программирования, библиотек и команд.

## 5. Англоязычные термины

Англоязычные термины допускается использовать в оригинальном написании, если они являются общепринятыми в технической среде или непосредственно связаны с интерфейсом инструмента.

При первом упоминании рекомендуется дать краткое русскоязычное пояснение, если оно облегчает понимание.

Пример:

> Инференс (inference) — применение обученной модели к новым данным.

В дальнейшем допускается использовать один выбранный вариант без повторного определения.

## 6. Термины предметной области

Термины, относящиеся к бизнес-логике системы, должны иметь согласованные определения.

Если одно понятие используется в разных модулях, его значение должно оставаться одинаковым либо различия должны быть явно описаны.

Нельзя использовать одно название для разных сущностей без пояснения. Если в системе существуют, например, пользователь, клиент и оператор, их роли и различия должны быть определены отдельно.

## 7. Обновление глоссария

При добавлении нового специализированного термина необходимо проверить:

1. Используется ли уже аналогичный термин.
2. Есть ли общепринятое определение.
3. Нужно ли объяснение для целевой аудитории.
4. Не противоречит ли новый термин существующим определениям.
5. Требуется ли обновление связанных документов.

## 8. Контрольный список

- [ ] Один термин обозначает одно понятие в заданном контексте.
- [ ] Технические названия написаны корректно.
- [ ] Новые специализированные термины объяснены.
- [ ] Синонимы не создают неоднозначности.
- [ ] Глоссарий соответствует текущему состоянию проекта.
