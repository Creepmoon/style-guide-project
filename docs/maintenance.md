# Проверка и сопровождение документации

## 1. Назначение

Этот раздел определяет порядок проверки, обновления и сопровождения документации проекта Design of an AI-Powered Information System.

Документация рассматривается как часть проекта и должна изменяться вместе с программным кодом, архитектурой, API и конфигурацией.

## 2. Ответственность за актуальность

Автор изменения отвечает за обновление документации, затронутой его изменениями.

Рецензент проверяет корректность внесённых правок и соответствие руководству по стилю.

Участники проекта должны сообщать об обнаруженных неточностях и не оставлять заведомо устаревшие инструкции без пояснения.

## 3. Когда необходимо обновлять документацию

Документацию следует проверять и при необходимости обновлять при следующих изменениях:

- изменение публичного API;
- добавление или удаление функций;
- изменение архитектуры компонентов;
- изменение схемы базы данных;
- изменение переменных окружения;
- изменение процесса установки или запуска;
- изменение алгоритма или версии модели машинного обучения;
- изменение требований к окружению;
- обнаружение ошибок в существующих инструкциях.

Если изменение не влияет на документацию, отдельная правка не требуется.

## 4. Локальная проверка

Перед отправкой изменений необходимо выполнить проверки, предусмотренные проектом.

Пример команд:

```bash
pymarkdown scan docs
mkdocs build --strict
```

Первая команда запускает проверку Markdown. Вторая собирает сайт документации в строгом режиме.

Если в репозитории используются дополнительные тесты или проверки ссылок, их также следует выполнить согласно инструкциям проекта.

## 5. Pull Request

Изменения документации передаются на рассмотрение через Pull Request.

Описание PR должно содержать:

- цель изменений;
- перечень изменённых документов;
- краткое описание существенных правок;
- результаты локальных проверок;
- известные ограничения, если они есть.

Рекомендуется делать небольшие тематические изменения, чтобы рецензент мог легко проверить каждую правку.

## 6. Ревью

Во время ревью проверяются:

- соответствие документации фактическому состоянию проекта;
- ясность и полнота текста;
- единообразие терминологии;
- корректность Markdown;
- работоспособность ссылок;
- точность примеров кода и конфигурации;
- отсутствие секретов и чувствительных данных;
- соблюдение правил данного стайлгайда.

Замечания должны указывать на конкретную проблему и, по возможности, содержать предложение по её устранению.

Автор рассматривает комментарии, вносит необходимые изменения и отправляет обновлённые коммиты в ту же ветку.

## 7. Автоматизация CI/CD

GitHub Actions используется для автоматической проверки и публикации документации.

В зависимости от конфигурации репозитория workflow должен:

1. Запускаться при создании или обновлении Pull Request.
2. Устанавливать необходимые зависимости.
3. Проверять Markdown.
4. Собирать сайт MkDocs.
5. Останавливать дальнейшие действия при ошибке проверки.
6. Публиковать документацию после успешного слияния изменений в основную ветку, если включён автоматический деплой.

Конкретное поведение определяется файлом workflow в каталоге `.github/workflows/`.

## 8. Условия слияния

Перед слиянием необходимо убедиться, что:

- изменения проверены рецензентом;
- существенные замечания устранены или согласованы;
- обязательные автоматические проверки прошли успешно;
- обновлённые документы доступны в навигации, если это требуется;
- изменения не содержат случайных файлов или секретных данных.

Дополнительные ограничения могут быть заданы правилами защиты основной ветки репозитория.

## 9. Проверка публикации

После слияния изменений необходимо:

- проверить результат выполнения GitHub Actions;
- убедиться, что этап публикации завершился успешно;
- открыть опубликованный сайт;
- проверить доступность изменённых страниц;
- проверить ссылки и отображение примеров.

Успешная сборка сама по себе не гарантирует, что все страницы корректно выглядят на опубликованном сайте.

## 10. Обработка ошибок

Если автоматическая проверка завершается ошибкой, необходимо изучить журнал выполнения и определить этап, на котором возникла проблема.

Исправление следует выполнить в исходной ветке PR, после чего автоматические проверки должны быть запущены повторно.

Если ошибка обнаружена после публикации, следует создать отдельное исправление и провести его через обычный процесс проверки.

## 11. Контрольный список

- [ ] Локальные проверки выполнены.
- [ ] Pull Request содержит описание изменений.
- [ ] Замечания рецензента рассмотрены.
- [ ] Автоматические проверки завершились успешно.
- [ ] Слияние выполнено согласно правилам репозитория.
- [ ] Опубликованная документация проверена.
